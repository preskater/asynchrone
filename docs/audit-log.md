# Audit log

Organization owners and admins get a first-class audit trail of everything
sensitive that happened in their workspace: who did it, on what, from which
address, and what changed. The decision is recorded in
[ADR 0027](adr/0027-customer-facing-audit-log.md).

## Where things live

| Concern                      | Location                                                                     |
| ---------------------------- | ---------------------------------------------------------------------------- |
| Table                        | `AuditLog` in every per-app schema (generated by `npm run split:prisma`)     |
| Shared read/write logic      | `packages/audit` (`@workspace/audit`, parameterized by the app's client)     |
| Action and entity catalogues | `packages/audit/src/actions.ts` (re-exported by the app)                     |
| The only write path          | `apps/copilot/lib/audit/record.ts` (`recordAudit`, `recordUserAudit`, …)         |
| Auth-endpoint coverage       | `apps/copilot/lib/audit/auth-audit.ts` (Better Auth `after` hook)                |
| Reads, filters, export       | `packages/audit/src/reader.ts`, `apps/copilot/lib/audit/service.ts`              |
| Cross-app fan-out            | `apps/copilot/lib/audit/fanout.ts`, `apps/copilot/lib/audit/remotes.ts`              |
| Retention policy and cleanup | `packages/audit/src/retention.ts`, `apps/copilot/lib/audit/prune.ts`             |
| Internal audit API           | `apps/copilot/app/internal/v1/audit/**`, `packages/audit/src/http.ts`            |
| Settings → Audit log         | `apps/copilot/components/audit/*`, tab `?tab=audit`                              |
| Daily cleanup                | `apps/copilot/app/api/cron/audit-retention/route.ts` (CronJob `audit-retention`) |
| Manual check                 | Each app mounts `/internal/v1/audit*`; `apps/copilot/e2e/audit-log.spec.ts` and the cross-app audit fan-out cover the trail. |

## Writing a row

Every mutating server action records its change with the shared helper, in the
same service method that performs the write:

```ts
import { AUDIT_ACTIONS } from "@/lib/audit/actions"
import { recordUserAudit } from "@/lib/audit/record"

await recordUserAudit(
  ctx,
  {
    action: AUDIT_ACTIONS.taskDeleted,
    entityType: "task",
    entityId: existing.id,
    entityLabel: existing.identifier,
    before: { title: existing.title, status: existing.status },
  },
  this.db // pass a transaction client when the mutation runs in one
)
```

Rules of thumb:

- `recordUserAudit` fills the organization, the actor (id, name, email) and the
  request IP / user agent. `recordSystemAudit` is for jobs and provider
  webhooks; `recordAudit` is for callers that already hold every field.
- One row per changed entity and per operation — a bulk delete writes one row
  per deleted file, not one per request.
- Snapshot `entityLabel` (task key, member email, file name): the target may be
  deleted later and the row must stay readable.
- Errors propagate. A mutation that cannot be audited fails instead of changing
  data silently.
- New actions go into `AUDIT_ACTIONS` and get a label under `actions.<action>`
  in `messages/{en,fr}/audit.json`. Unknown actions still render, with their raw
  value as the label, so older rows survive a rename.

Organization member, role and invitation changes go through Better Auth's HTTP
endpoints rather than a server action. They are covered by the `after` hook in
`apps/copilot/lib/auth.ts`, which sees the acting session (Better Auth's
`organizationHooks` only receive the target member, which is not enough for an
audit trail).

Project messages and task comments write `project.message.added` / `task.comment.added`; they remain visible in the project activity feed too. Chat messages, calendar events and meeting requests write their own audit rows in the owning app; the project, client and employee mutations already did.

## Reading it

`GET`-shaped server actions in `apps/copilot/actions/audit.ts` power the page:

| Action                    | Purpose                                                       |
| ------------------------- | ------------------------------------------------------------- |
| `listAuditLogAction`      | One keyset page (50 rows) for the active filter, plus a total |
| `loadAuditFacetsAction`   | Distinct actions, target types and actors in the window       |
| `exportAuditLogAction`    | CSV or JSON of the active filter, capped at 5000 rows         |
| `getAuditRetentionAction` | Effective window and whether it is configurable               |
| `setAuditRetentionAction` | Enterprise override, owner only                               |

Access is checked twice: the `audit:read` capability (owners and admins; members and viewers get a 403) and
the `auditLog` entitlement. Client-portal accounts never reach the workspace.
The filter days are **UTC** days, so `from=2026-10-01&to=2026-10-01` covers
`2026-10-01T00:00:00Z` through `2026-10-01T23:59:59.999Z`.

An export over the cap is truncated and the UI warns; narrow the date range to
collect the rest.

## One trail, many databases

Each app writes the row in the same transaction as the data it describes, in its
own `AuditLog` table. `@workspace/audit` owns the shared logic and is
parameterized by the app's database client, so the table stays local while the
page stays global.

Every app exposes the same internal API (mounted in Copilot at
`/internal/v1/audit`):

| Method | Path                        | Scope                  | Purpose                              |
| ------ | --------------------------- | ---------------------- | ------------------------------------ |
| `GET`  | `/internal/v1/audit`        | `internal:audit:read`  | One keyset page for one organization |
| `GET`  | `/internal/v1/audit/facets` | `internal:audit:read`  | Filter options                       |
| `GET`  | `/internal/v1/audit/export` | `internal:audit:read`  | Up to 5000 rows for a merged export  |
| `POST` | `/internal/v1/audit/prune`  | `internal:audit:write` | Delete expired rows at plan cutoffs  |

`AuditClient` in `@workspace/contracts` is the typed caller. Copilot fans out to
every app whose `*_APP_URL` is configured (`PROJECTS_APP_URL`,
`CALENDARS_APP_URL`, …, using the Copilot OAuth client), merges pages by
`(createdAt, id)`, and keeps a composite cursor so each app resumes at its own
last row. A slow or down app yields `partial: true` and an `unavailableApps`
entry; the rest of the trail still renders. With no app origin configured, the
fan-out is local and the behaviour is unchanged.

Exports merge the JSON rows from every app before formatting (CSV/JSON), and a
partial export is never presented as complete. Retention runs locally through
`pruneAuditLogs` and then fans the same plan cutoffs to the domain apps through
`pruneRemoteAuditLogs`; a failed app is reported and retried on the next run.
`PlatformAuditEvent` stays in the control tower's database and is never part of
this fan-out.

## Retention

| Plan       | Window                                                                                 |
| ---------- | -------------------------------------------------------------------------------------- |
| Free       | 30 days                                                                                |
| Team       | 365 days                                                                               |
| Enterprise | 730 days, overridable between 30 and 3650 (`organization.metadata.auditRetentionDays`) |

A Team trial counts as Team. The window is enforced by the daily
`/api/cron/audit-retention` job (`pruneAuditLogs`), which walks every
organization, deletes rows older than its cutoff in batches of 5000, and caps
each organization at 20 batches per run so a backlog never holds a long lock —
the next run continues where the last one stopped. It only touches `AuditLog`:
the control tower's `PlatformAuditEvent` is a separate table with its own
lifecycle and is never pruned here.

Rows are still written on plans that cannot read them (Free, Team) so an
upgrade immediately shows the history inside the window, and so the table never
grows without bound.

## Out of scope

Real-time streaming, shipping events to an external SIEM (a future Enterprise
option), and platform-level auditing, which lives in the control tower. A plan
change applied from the control tower is recorded as a `PlatformAuditEvent`
there; the billing path records `organization.plan.changed` here.
