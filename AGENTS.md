# Agents

## Repository

- Turborepo + npm workspaces monorepo. Apps: `apps/copilot` (package `copilot`, the customer SaaS and identity/OAuth server, Next.js 16 App Router, React 19), `apps/control-tower` (package `control-tower`, internal platform administration) and `apps/landing` (package `landing`, the stateless public marketing site at `asynchrone.space`). Shared packages: `packages/db` (`@workspace/db`), `packages/ui` (`@workspace/ui`), `packages/i18n` (`@workspace/i18n`), `packages/next-config` (`@workspace/next-config`), `packages/eslint-config`, `packages/typescript-config`.
- Run tasks from the repo root through Turbo: `npm run dev|build|lint|typecheck|format`. Target one workspace with `--workspace=copilot`, `--workspace=control-tower` or `--workspace=landing` (or `-w`).
- `main` is protected: land changes via PR. The `ci` job (`.github/workflows/turbo.yml`) runs typecheck → lint → build; `.github/workflows/helm.yml` lints and renders the chart.

## Verify before finishing

- There is no single root `test` script — use the targeted commands below and do not add a speculative broad suite.
- Run, in order: `npm run lint && npm run typecheck && npm run build` (matches CI), plus `npm run test:unit --workspace=copilot` and `npm run test:unit --workspace=@workspace/contracts` (vitest; `*.unit.test.ts` next to the code). `npm run test:e2e --workspace=copilot` runs Playwright against a migrated database (CI does this in the `e2e` job).
- Cross-domain contracts (needs a migrated PostgreSQL; no browser): `npm run test:contracts`. The suite lives in `apps/copilot/scripts/contracts` and pins package exports, the member directory, notifications, recents, search, export/deletion and the MCP/assistant tool surface; it also replays the issue #40 cross-org/impersonation attacks. CI runs it in the `contracts` job. See `docs/contract-tests.md`.
- Workspace boundaries: `npm run check:boundaries` fails on a package→app import, an app→app import, an undeclared `@workspace/*` dependency, a relative import that escapes its workspace, or a cross-`@workspace/db-*` import. CI runs it after lint.
- Per-app migrations: `npm run db:create && npm run migrate:deploy && npm run verify:migrations` (needs a live PostgreSQL). The migrate image runs the monolith migration first, then the ordered per-app orchestrator.
- Database split (maintenance window; needs source and target databases): `npm run split:databases -- --dry-run`, then `--all`. Large-object OIDs are preserved. See `docs/database-split.md`.
- The Turbo `generate` task (`prisma generate` → `packages/db/lib/generated/prisma`) is a dependency of `build`/`typecheck`/`dev`. After editing `schema.prisma`, run `npm run generate --workspace=@workspace/db`.
- Manual storage check (needs a live DB): `npm run verify:large-object --workspace=copilot`.
- Manual messaging check (needs a live DB; attachment upload/download, conversation membership, unread state and cross-organization authorization): `npm run verify:messaging --workspace=copilot`.
- Manual client-portal check (needs a live DB; client-member scope, cross-organization reads, portal document upload/download, audit and team notification): `npm run verify:portal --workspace=copilot`.
- Manual repository-sync check (needs a live DB; exercises GitHub/GitLab against an in-process mock): `npm run verify:repository-sync --workspace=copilot`.
- Manual Team trial check (needs a live DB; start, abuse checks, D-3 reminder, idempotent expiry): `npm run verify:trial --workspace=copilot`.
- Manual organization-deletion check (needs a live DB; request/cancel rules, the 30-day grace period, no orphan rows, every large object unlinked): `npm run verify:organization-deletion --workspace=copilot`.
- Manual data-export check (needs a live DB; owner-only requests, archive contents against the database, no secrets, expiry and cleanup on organization deletion): `npm run verify:data-export --workspace=copilot`.
- Manual authorization check (needs a live DB; replays the issue #40 cross-org/impersonation attacks): `npx tsx scripts/verify-authorization.ts` (from `apps/copilot`).
- Legal copy parity (no DB needed): `npm run verify:legal-copy --workspace=landing`. It fails when the `en` and `fr` legal documents disagree on a key, or when a table or list in `legal.json` is malformed.
- Landing stateless invariant (no DB needed): `npm run verify:stateless --workspace=landing`. It fails when `apps/landing` imports `@workspace/auth`, `@workspace/db*`, `@workspace/oidc`, `@workspace/service-auth`, `@workspace/sagas`, `@workspace/app-shell`, Prisma, `better-auth` or `pg`, accesses a cookie, or declares such a dependency.
- Landing unit tests (no DB needed): `npm run test:unit --workspace=landing`. They pin the legacy apex → Copilot redirect map and the stateless import graph.
- Legal PDFs: `npm run legal:pdfs --workspace=landing` regenerates `apps/landing/public/downloads/legal` from the same copy (needs Chromium; `npx playwright install chromium` once). Commit the PDFs with the copy that produced them — see `docs/legal/README.md`.
- Control-tower auth invariant (no DB needed): `npm run verify:auth-config --workspace=control-tower`. It fails if cross-subdomain cookies are enabled, sign-up is opened, the Copilot auth secret is reused, or the 2FA plugin is missing.
- Manual audit-log check (needs a live DB; creates and deletes throwaway organizations): `npm run verify:audit-log --workspace=copilot`. It checks one-row-per-mutation coverage, role/entitlement gating, filters, the export cap, the Enterprise retention override and the cleanup job. The cleanup job walks every organization, so run it against a development database.
- Manual platform-authorization check (needs a live DB): `npm run verify:platform-authorization --workspace=control-tower`. It covers role resolution, the IP allowlist, single-use handoff claims, the cutover invariant (only platform accounts in the platform database) and a real Better Auth sign-in against it.
- Control-tower database cutover (needs a live DB; dry run by default): `npm run cutover:control-tower --workspace=control-tower -- --dry-run`, then `--apply`, `--verify`. It copies only platform operators (plus accounts, sessions, TOTP, `platformAuditEvent`, `platformHandoff`) into `asynchrone_control_tower`; `--user <email> --apply` provisions one operator. See `docs/control-tower-database.md` for the maintenance window and rollback.

## Environment & data

- Env lives in `apps/copilot/.env` (Next loads it from the app cwd; `packages/db/prisma.config.ts` loads it explicitly, falling back to a package-local `.env`). Start from `apps/copilot/.env.example`. `CONTROL_TOWER_URL` (the control tower origin) is used by the "Stop impersonating" flow.
- The control tower has its own `apps/control-tower/.env` (`apps/control-tower/.env.example`): `CONTROL_TOWER_DATABASE_URL` (its own database, never `DATABASE_URL`), `BETTER_AUTH_URL` (its own origin), `CONTROL_TOWER_BETTER_AUTH_SECRET` (≥32 chars, different from `BETTER_AUTH_SECRET`), `PLATFORM_APP_URL` (Copilot's origin). `DATABASE_URL` in that file is only the cutover script's source.
- `docker compose` loads `apps/copilot/.env` into the `copilot` container (its `environment` block still overrides `DATABASE_URL`/`BETTER_AUTH_URL`), so local dev and Docker share `BETTER_AUTH_SECRET`; rotating that secret breaks the encrypted JWKS rows in the DB — clear the `jwks` table to regenerate them.
- One `Dockerfile` builds any app with `--build-arg APP=copilot|control-tower|landing`; `docker compose` serves the landing on 3002, the Copilot app on 3003 and the control tower on 3001. `.dockerignore` excludes `.env` files at any depth — never bake local secrets into an image.
- `generate` and the `copilot`/`control-tower` builds require `DATABASE_URL`, `BETTER_AUTH_SECRET`, and `BETTER_AUTH_URL` to be set; CI and Docker use non-connecting placeholders. The landing is stateless and builds with none of them (CI has a dedicated `landing` job that proves it).
- When adding an env var, also add it to the `env` arrays in `turbo.json` (build + dev) so Turbo passes it through, update `.env.example`, and add a build-time placeholder in `Dockerfile` / `.github/workflows/turbo.yml` if it is read at build time.
- `DATABASE_POOL_MAX` defaults to `3`. One shared `pg.Pool` in `packages/db/src/prisma.ts` serves both Prisma and the large-object code; `apps/copilot/lib/prisma.ts` only re-exports it.

## Deployment

- `.github/workflows/docker.yml` publishes four GHCR images: `asynchrone-space-copilot` (Copilot runner), `asynchrone-space-control-tower` (control-tower runner), `asynchrone-space-landing` (landing runner) and `asynchrone-space-migrate` (Dockerfile `migrate` stage).
- Helm charts live in `charts/`: `asynchrone-space` is the umbrella (migration hook and production values); `asynchrone-space-landing`, `asynchrone-space-copilot` and `asynchrone-space-control-tower` are the app subcharts. The landing ingress owns `asynchrone.space` and redirects `www` to the apex; Copilot serves `copilot.asynchrone.space`. Install/upgrade from the root with `helm dependency build charts/asynchrone-space` then `helm upgrade --install asynchrone-space charts/asynchrone-space -n asynchrone-space --set global.imageTag=sha-…`. The packaged subcharts under `charts/asynchrone-space/charts/` are committed (Git-based chart sources such as Rancher never run `helm dependency build`); after editing a subchart, run `helm dependency build` and commit the archives — CI verifies they match the sources.
- The chart requires the existing Secrets `asynchrone-space-copilot-secrets` (DATABASE_URL, BETTER_AUTH_SECRET, CRON_SECRET, optional provider keys) and `asynchrone-space-control-tower-secrets` (CONTROL_TOWER_DATABASE_URL, CONTROL_TOWER_BETTER_AUTH_SECRET). Never put secrets in values or templates.
- The pre-install/pre-upgrade `asynchrone-space-migrate` Job runs `prisma migrate deploy`; the Copilot subchart owns the five CronJobs (`uploads-sweep`, `repository-sync`, `trial-expiry`, `organization-deletion`, `data-exports`) that replaced the former Vercel crons. See `docs/deployment/helm.md` and ADR 0019.
- Verify chart changes with `helm dependency build charts/asynchrone-space && helm lint --strict charts/asynchrone-space --set global.imageTag=test && helm template asynchrone-space charts/asynchrone-space --set global.imageTag=test`.

## Prisma / database

- Prisma 7 with the `@prisma/adapter-pg` driver adapter (not the default connector).
- Schema and migrations live in `packages/db/prisma`; apply with `cd packages/db && npx prisma migrate deploy`. Create migrations from `packages/db`.
- `@workspace/db` validates only database env (`DATABASE_URL`, `DATABASE_POOL_MAX`). App-specific requirements stay in each app's own `lib/env.ts`.
- File bytes are stored as PostgreSQL large objects in the same DB as metadata — no external object store (Vercel Blob was removed). See `apps/copilot/lib/large-object.ts`.

## Audit log

- `AuditLog` is the customer-facing trail (Settings → Audit log) and exists in every per-app schema. Shared logic lives in `@workspace/audit` (`packages/audit`), parameterized by the app's database client. Write it only through `apps/copilot/lib/audit/record.ts` (`recordUserAudit` for server actions, `recordSystemAudit` for jobs/webhooks), never with `prisma.auditLog.create` — that is what keeps the page, the export and the retention job consistent.
- Every app exposes `/internal/v1/audit`, `/audit/facets`, `/audit/export` and `/audit/prune` through `packages/audit/src/http.ts`, gated by `internal:audit:read` / `internal:audit:write`. Copilot merges them with `apps/copilot/lib/audit/fanout.ts` (composite cursor, partial results); configure `*_APP_URL` to enable a domain app.
- The mutation that performs a change records the row itself (one row per changed entity), snapshots `entityLabel`, and lets a failed audit write fail the action.
- New actions go into `AUDIT_ACTIONS` and get `Audit.actions.<action>` labels in `packages/i18n/messages/{en,fr}/audit.json`; unknown actions fall back to their raw value.
- Member, role and invitation changes go through Better Auth, so they are audited from the `after` hook in `apps/copilot/lib/auth.ts` (`apps/copilot/lib/audit/auth-audit.ts`).
- Reads and exports are gated by `roleRank >= admin` and the `auditLog` entitlement (Enterprise). Retention is 30 / 365 / 730 days (Free / Team / Enterprise, overridable on Enterprise) and is pruned by the `audit-retention` CronJob, which must never touch `PlatformAuditEvent`. See `docs/audit-log.md` and ADR 0027.

## Control tower

- Internal app at `apps/control-tower` (port 3001). Platform roles live in the comma-separated `user.role`: `platform_admin` (full) and `platform_support` (read-only for now). Grant one with `npm run grant:platform-role --workspace=control-tower -- --email you@example.com`; the account must then enroll a TOTP device at `/setup-2fa`.
- It owns `asynchrone_control_tower` (`@workspace/db-control-tower`) for platform users, sessions, accounts, TOTP, `PlatformAuditEvent` and its `PlatformHandoff` copy. It never imports `@workspace/db` (enforced by `check:boundaries`); every customer read model comes from `/internal/v1/admin/*` through `IdentityAdminClient`. See `docs/control-tower-database.md` and ADR 0034.
- Operators are provisioned by signing up in Copilot, then `npm run cutover:control-tower --workspace=control-tower -- --user you@example.com --apply` and a role grant. The full cutover/rollback runbook is `docs/control-tower-database.md`.
- Every platform role requires TOTP (`twoFactor` plugin; `TwoFactor` table and `user.twoFactorEnabled`). `requirePlatformContext()` redirects unenrolled operators to `/setup-2fa` and rejects server actions; `requirePlatformSession()` is the 2FA-free variant used only by that page.
- Optional `PLATFORM_ALLOWED_IPS` (comma-separated IPv4/CIDR or `*`) restricts the control tower to known networks as defense in depth. Unset allows every address; in-app auth still applies.
- Its Better Auth instance is deliberately separate: own secret, own host-only cookie (`asynchrone-space-control-tower.session_token`), sign-up disabled, no `jwt`/`mcp`/`organization` plugins. **Never enable `advanced.crossSubDomainCookies`** — see ADR 0018 and `verify:auth-config`.
- Pages guard with `requirePlatformContext()`; anonymous users go to `/sign-in`, signed-in users without a platform role get `notFound()`. Server actions use `requirePlatformContext({ surface: "action" })` / `withPlatformAction`.
- Platform mutations write `PlatformAuditEvent` rows (never the org-scoped `AuditLog`). Impersonation uses the single-use `PlatformHandoff` table, not a shared cookie.
- Platform mutations are server actions under `apps/control-tower/actions/`. Each uses `withPlatformAction`, enforces `platform_admin` for destructive changes (`platform_support` may revoke sessions), appends a `PlatformAuditEvent`, and revalidates the affected path. Customer identity changes go through Copilot's `/internal/v1/admin/*` with `IdentityAdminClient` (`internal:identity:admin`), never a direct identity-database write.
- Impersonation is a single-use handoff, never a shared cookie: the control tower stores a hashed token in `PlatformHandoff` and redirects to `${PLATFORM_APP_URL}/api/platform/handoff?token=…`; the Copilot route claims it, creates a 1-hour session with `impersonatedBy`, and signs its own cookie. `apps/copilot/app/[locale]/(app)/layout.tsx` shows the banner and deletes the session once it is an hour old; `/api/platform/stop-impersonating` deletes it and returns to `CONTROL_TOWER_URL`.
- `apps/copilot/lib/auth.ts` registers the same `admin()` plugin (roles map + `adminRoles: ["platform_admin"]`) so bans apply to customer sign-in.

## Code layout & conventions

- Path aliases: `@/*` → `apps/copilot/*`, `@workspace/ui/*` → `packages/ui/src/*`. UI imports require `transpilePackages` (already set in `next.config.ts`).
- `@workspace/contracts` owns the app/database registry and the versioned `/internal/v1` schemas. Import from the package root for shared metadata; `@workspace/contracts/server` is server-only because it reads runtime app origins. Internal APIs must use these contracts rather than inventing their own shapes. See `docs/architecture/domain-apps.md`.
- Per-app databases live in `@workspace/db-<domain>` packages, with `@workspace/db-core` for the shared pool. Their Prisma schemas are generated by `npm run split:prisma`; do not hand-edit them. `npm run verify:prisma-schemas` validates all schemas. See `docs/databases.md`.
- Plan and trial rules are dependency-free in `@workspace/core/plans` and `@workspace/core/trial` (`entitlementsFor`, `parsePlan`, `effectivePlan`, `monthWindow`, …), so every app can resolve the same plans without importing a database package.
- UI is shadcn/ui on **Base UI** primitives (not Radix) with Tailwind. Owned components live in `packages/ui/src/components`.
- `pg` and `pg-large-object` are listed in `serverExternalPackages`; keep them out of client code.
- Rate limits are shared across replicas through the `rateLimit` table (ADR 0022): use `rateLimit`/`assertRateLimit` from `packages/core/src/rate-limit.ts` and choose `failOpen` per call site. Better Auth limits auth endpoints through the same table.
- Sign-up abuse controls (`packages/auth/src/signup-policy.ts`, wired through `@workspace/auth` and `apps/copilot/lib/auth.ts`): Cloudflare Turnstile on `/sign-up/email` and `/request-password-reset` when `TURNSTILE_SECRET_KEY` is set (`TURNSTILE_SITE_KEY` must be set too, or the app refuses to boot), a disposable-domain blocklist plus `SIGNUP_BLOCKED_EMAIL_DOMAINS`, and optional `SIGNUP_INVITE_ONLY`. The `user.create.before` hook applies them to OAuth sign-ups too; keep it that way when adding a provider.
- Billing lives in `apps/copilot/lib/billing` (repository/provider/notifier ports, `service.ts` for the state machine, `plans.ts` for status → plan). Plan enforcement reads `subscription.plan` first and falls back to `organization.metadata.plan` through `resolvePlan()` in `packages/organization/src/entitlements.ts` (bound in `apps/copilot/lib/organization/entitlements.ts`) — every entitlement goes through it. Stripe webhooks arrive at `apps/copilot/app/api/webhooks/stripe/route.ts` (signature-verified, idempotent through `BillingEvent`; a failed delivery is re-claimed on Stripe's retry). Manual/Enterprise grants set `manualOverride` and are made from the control tower. See `docs/billing.md` and ADR 0023.
- The workspace shell (resolver, banners, nav, recents and appearance) lives in `@workspace/app-shell`; apps pass their app-local session and domain slots. Domain screens load their own data.
- Cross-domain services are port-parameterized packages: `@workspace/storage` (large objects for the files app), `@workspace/notifications`, `@workspace/integrations` (provider clients; tokens stay in the owning app), `@workspace/ai` (agent, pricing and quota ledger), `@workspace/appearance` (organization preferences), `@workspace/billing` (plans and subscription state machine) and `@workspace/audit`. The owning app binds its database client, pool, provider or notifier in `apps/copilot/lib/*`; packages never open another app's database.
- Calendars and meetings live in `@workspace/calendars` (calendars, members, events, attendees, date helpers) and `@workspace/meetings` (settings, client requests, slots, provider adapters). Both are Next-free and take structural `CalendarDb`/`MeetingDb` ports and a `MeetingNotifier`; `apps/copilot/lib/{calendars,meetings}/index.ts` bind the Prisma client and the notification inbox. The workspace layout only mounts an empty calendar provider; the calendars screen loads its own data.
- Projects/tasks/templates/labels/comments and the GitHub/GitLab repository sync live in `@workspace/projects` (repository, service, schemas, types, UI). `apps/copilot/lib/{projects,integrations}` are thin adapters that bind the Prisma client, audit writer, notification inbox and `BETTER_AUTH_URL`; server actions stay in `apps/copilot/actions/*` until `apps/projects` exists (#160). The package takes the actions as a port (`ProjectActions`) and never imports `@/actions/*`.
- Organization roles, permissions, entitlements, shell queries, paths and the member-directory contract live in `@workspace/organization`; `apps/copilot/lib/organization/*` files are app adapters.
- The files domain lives in `@workspace/files`: the file tree, versions, shares, chunked upload sessions (ADR 0010), the screens and the large-object unlink path used by data export and organization deletion. `apps/copilot/lib/files.ts` binds the database, audit writer, plan checks, quota reader, rate limiter and large-object store; `apps/copilot/components/files-provider.tsx` binds the actions, member directory and workspace navigation.
- Clients/contacts/deals/pipelines/fields/activities/documents live in `@workspace/clients`; employee profiles/attendance/leave/balances/settings/salary/capacity live in `@workspace/employees`. Both own access checks, schemas, services, CSV/date helpers, types and UI. `apps/copilot/lib/{clients,employees}/index.ts` are thin adapters that bind the Prisma client, `recordAuditMany`/`withActorIdentity` and (clients only) the notification inbox; the `(clients)` layout and the employees page inject the server actions as `ClientActions`/`EmployeeActions`, so no package component imports `@/actions/*`. Salary and payroll stay behind `isAdmin`/`requireAdmin`.
- The messaging domain lives in `@workspace/messaging`: conversations, members, messages, reactions, threads, attachments, unread state and the chat screens. `apps/copilot/lib/messaging.ts` binds the database and the large-object store (attachments upload through `@workspace/files` and live in `@workspace/storage`); `apps/copilot/components/messaging-provider.tsx` binds the server actions and member directory, and `apps/copilot/components/messaging-workspace.tsx` binds the workspace navigation and the meetings slots. Read/write services feed the assistant and MCP tools.
- The client portal domain lives in `@workspace/portal`: portal context and client-member authorization, dashboard/project/task/document read models, document upload and download, the shared project thread and task comments, portal access management and the client meetings read model. `apps/copilot/lib/portal/index.ts` binds Prisma, `@workspace/storage`, `@workspace/files`, `@workspace/projects`, `@workspace/meetings`, Better Auth invitations, audit and notifications; `apps/copilot/lib/portal/context.ts` resolves `Member.clientId` from the session, and `apps/copilot/app/[locale]/portal/layout.tsx` passes the server actions through `PortalActions`. Portal routes and APIs stay in Copilot (there is no `apps/portal`), and portal accounts (`role=client`) must never reach the internal workspace.
- The Better Auth server configuration and shared session helpers live in `@workspace/auth`; `apps/copilot/lib/auth.ts` only injects the identity database, mailers, audit writers, plan checks and OAuth server resources.
- Customer 2FA uses the same `twoFactor` plugin mapped to its own `customerTwoFactor` table and `user.customerTwoFactorEnabled` column; never point it at the control tower's `twoFactor` table (different encryption secret). See `docs/two-factor.md`.
- Copilot is the OAuth 2.1/OIDC authorization server through `mcp()`; never register `oauthProvider()` alongside it. App resources, scopes, token lifetimes and claims live in `apps/copilot/lib/oauth`; see `docs/oauth-server.md`.
- Workspace apps consume `@workspace/oidc` for the authorization-code flow, host-only session cookie, token refresh, JWKS verification and back-channel logout. Never implement a second OAuth client. See `docs/oidc-client.md`.
- First-party OAuth clients are declared in `apps/copilot/lib/oauth/clients.ts` and provisioned/rotated with `npm run oauth:clients --workspace=copilot`. Never create them by hand. See `docs/oauth-clients.md`.
- Internal service calls use `@workspace/service-auth`: OAuth client credentials, audience-bound tokens, a per-audience cache and a verifier for `/internal/v1/*`. Never use a shared secret or an unauthenticated call. See `docs/internal-service-auth.md`.
- Cross-database export/deletion are durable sagas in `@workspace/sagas`: identity state in `organizationDeletionJob` / `userDeletionJob` / `dataExportApp`, per-app idempotent endpoints, retries that resume at the failed app, identity deleted last, and an export marked ready only when every part is complete. See `docs/domain-app-sagas.md`.
- Notifications are created in Copilot with `(organizationId, idempotencyKey)`; search is a per-app `/internal/v1/search` fanned out with timeouts and partial results. Recents stay per app. See `docs/search-and-notifications.md`.
- The identity internal API is `apps/copilot/app/internal/v1/**` (identity DB, `internal:identity:read`) and its typed client is `IdentityClient` in `@workspace/contracts`. Use `invalidate(organizationId)` after member/role mutations. See `docs/identity-api.md`.
- Organization deletion is a two-step flow: an owner schedules it (`lib/organization/deletion-service.ts`, `organization.deletionScheduledAt`), every member sees a banner, and the daily `organization-deletion` cron deletes overdue organizations, their large objects and the FK-less rows (`uploadSession`, `platformHandoff`). Better Auth's own `organization.delete` is disabled so nothing bypasses the grace period.
- i18n uses next-intl with `localePrefix: "always"` (en default, fr). Add every user-facing string to both `packages/i18n/messages/en` and `packages/i18n/messages/fr`; blog/content MDX is mirrored under `apps/landing/content/<type>/<locale>`.
- Legal documents are data, not JSX: sections live in `apps/landing/lib/landing/legal.ts`, copy in `packages/i18n/messages/{en,fr}/legal.json`, printable versions in `apps/landing/public/downloads/legal`. See `docs/legal/README.md` before adding a document or a sub-processor.
- The landing must never import `@workspace/auth`, `@workspace/db`, `@workspace/oidc` or Prisma: it has no session and no database. Header account actions link to `copilot.asynchrone.space`, configured at build time with `NEXT_PUBLIC_WORKSPACE_URL` (`apps/landing/.env.example`); canonical URLs, `robots.txt` and `sitemap.xml` use `NEXT_PUBLIC_SITE_URL`. `createNextConfig({ workspacePackages })` keeps its transpile list to `@workspace/ui` and `@workspace/i18n`.
- `apps/landing/proxy.ts` redirects legacy apex workspace paths to Copilot with a 308: the auth flows (`sign-in`, `sign-up`, `forgot-password`, `reset-password`, `two-factor`, `verify-email`, `consent`), onboarding, `select-organization`, `accept-invitation`, `portal`, `settings`, `search`, `help`, `feedback`, `mcp`, `api/assistant` and organization-scoped sections (`/<orgSlug>/{settings,search,help,feedback,projects,files,messages,calendars,employees,clients,hr}`). Copilot serves `/search`, `/help` and `/settings` (which redirects to `/settings/account`) as workspace-wide fallbacks. `MARKETING_SEGMENTS` protects the marketing routes (about, blog, careers, contact, FAQ, features, legal, pricing) from ever being shadowed; the redirect map is unit-tested.
- The landing is the only indexable app: it serves `robots.txt` (allow all) and a localized `sitemap.xml`. Copilot sends `X-Robots-Tag: noindex, nofollow` on every response, disallows `/` in `apps/copilot/app/robots.ts` and sets `robots: { index: false }` in its metadata; the control tower does the same.
- The assistant/MCP endpoint is at `apps/copilot/app/mcp/route.ts` (not under `/api`) and is excluded from the i18n middleware in `apps/copilot/proxy.ts`. Other API routes are under `apps/copilot/app/api/*`.
- ESLint is flat-config per workspace (`eslint.config.js`); the root `.eslintrc.js` only holds ignores. Prettier config is `.prettierrc` (with Tailwind class sorting); root `format` only covers `**/*.{ts,tsx}`.
